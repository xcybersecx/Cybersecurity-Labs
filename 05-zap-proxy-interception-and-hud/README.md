# OWASP ZAP Proxy, HUD and Request Interception Practical

**Completed:** 23 August 2026  
**Environment:** Kali Linux and Firefox  
**Tool:** OWASP ZAP 2.17.0  
**Training Target:** `testaspnet.vulnweb.com`

## Overview

This practical focused on understanding OWASP ZAP as an intercepting web proxy rather than just seeing it as a vulnerability scanner.

The basic traffic flow was:

```text
Browser → ZAP → Web Server
Web Server → ZAP → Browser
```

Because ZAP sits between the browser and server, it can show the requests and responses that are normally hidden behind ordinary browser activity.

During the practical I worked with the ZAP Root CA certificate, Manual Explore, the HUD, passive and active scanning concepts, the Sites tree, request/response inspection and breakpoints.

The training target was deliberately vulnerable and authorised for security testing.

---

## 1. Configuring the ZAP Root CA Certificate

Firefox was configured to trust the ZAP Root CA certificate.

I learned why this matters for HTTPS. HTTPS traffic is encrypted, so if ZAP is going to inspect it, ZAP has to act as an intermediary between Firefox and the target.

Firefox therefore needs to trust certificates generated by ZAP during interception.

The important idea for me was:

**HTTPS interception requires the browser to trust the proxy's certificate authority.**

## 3. The ZAP HUD

HUD stands for **Heads Up Display**.

It places ZAP controls around the application inside the browser so that some security-testing functions can be used without constantly switching back to the main ZAP window.

I successfully launched the HUD and completed part of its built-in tutorial.

The HUD controls appeared in frames around the target. They could expand when selected and could also be hidden when they got in the way.

The tutorial included a small key-finding exercise, which helped me become more familiar with navigating the HUD while still interacting with the application.

## 4. Passive vs Active Scanning

This session also introduced the difference between passive and active scanning.

### Passive scanning

Passive scanning analyses traffic that is already passing through ZAP.

ZAP observes the requests and responses without deliberately sending attack payloads.

```text
Passive = observe and analyse
```

### Active scanning

Active scanning deliberately sends specially constructed requests or payloads to test the application.

```text
Active = actively test
```

The distinction also matters for authorisation. Active scanning should only be used against systems where testing is permitted.

## 5. The Sites Tree

ZAP builds a hierarchical **Sites tree** from resources it discovers.

Initially I was opening individual entries instead of expanding the branches properly.

Once I understood the structure, I could see resources beneath the site, including JavaScript files associated with the HUD tutorial.

The Sites tree helped me understand that an application is made up of more than the page currently visible in the browser. It can contain pages, scripts, directories, endpoints and other resources.

## 7. Disabled and Read-Only Fields

The HUD tutorial demonstrated that HTML form fields can be editable, disabled or read-only.

ZAP's Show/Enable functionality could expose or enable fields that the normal browser interface did not allow me to edit.

This introduced an important security lesson:

**A restriction in the browser is not automatically a security boundary.**

The browser interface may prevent a user from changing something, but the HTTP request underneath it may still be altered.

Security-sensitive input therefore still has to be validated by the server.

---

## 8. Request Interception Exercise

The HUD tutorial included an HTML5 number field that accepted values between:

```text
1 and 100
```

The idea was to enter a valid value in the browser, intercept the request in ZAP and then change the value before the request reached the server.

Conceptually:

```text
Browser accepts: number=50
        ↓
ZAP intercepts the request
        ↓
Tester changes: number=50
to:             number=ZAP
        ↓
ZAP forwards the modified request
        ↓
Server receives: number=ZAP
```

This made the client-side/server-side distinction much clearer.

The browser can enforce a rule such as "numbers only", but ZAP operates on the HTTP request after the browser has created it.

So:

**Client-side validation can improve the interface, but the server cannot rely on it for security.**

## 11. History, Break and Breakpoints

The troubleshooting actually helped me understand three ZAP concepts that I had initially been mixing together.

### History

**History = traffic that has already passed through ZAP.**

I can inspect it afterwards, but it is no longer waiting for me to decide what happens next.

### Break

**Break = traffic currently paused.**

This is where a request or response can be inspected or modified before it continues.

### Breakpoints

**Breakpoints = rules telling ZAP which traffic to interrupt.**

That distinction made the interception workflow much easier to understand.

---

## 12. Break Controls

I also learned the purpose of several controls used when traffic is paused.

### Step

Forwards the current message and breaks again on the next relevant request or response.

### Continue

Forwards the current message and continues until another breakpoint is encountered.

### Drop

Stops the intercepted request or response from continuing.

These controls showed me that an intercepting proxy can do more than simply display traffic. It can pause and influence the communication between browser and server.

---

## 13. HTTP Status Codes

Two codes appeared repeatedly during the session.

### 200 OK

```text
200 OK
```

means the HTTP request was processed and a valid response returned.

As I had learned in the previous practical, that does not automatically mean the user's intended application action succeeded.

### 504 Gateway Timeout

```text
504 Gateway Timeout
```

appeared several times while trying to reach the training target.

I understood this as a server or intermediary not receiving the required upstream response in time.

The session also helped reinforce the broad status-code groups:

```text
2xx = success
3xx = redirection
4xx = request/client/access/resource-related errors
5xx = server/upstream errors
```

Codes I was learning included:

```text
200 201
301 302
400 401 403 404
500 502 503 504
```

## What I Learned

This practical helped me understand ZAP as more than a scanner.

The main things I learned were:

- ZAP can sit between a browser and web server as an intercepting proxy;
- HTTPS interception requires Firefox to trust ZAP's Root CA;
- the HUD puts ZAP controls into the browser;
- passive scanning observes existing traffic;
- active scanning deliberately tests a target;
- the Sites tree maps resources ZAP has discovered;
- GET and POST represent different HTTP interactions;
- disabled/read-only browser fields should not be treated as security controls;
- HTTP requests can potentially be modified after the browser creates them;
- server-side validation is therefore important;
- History shows traffic that has already passed;
- Break shows traffic currently paused;
- Breakpoints decide which traffic ZAP should interrupt;
- Step, Continue and Drop control what happens to intercepted traffic;
- HTTP status codes need to be interpreted in context; and
- network or tool problems should be diagnosed rather than hidden from the report.

## Key Takeaway

The most important model from this practical was:

```text
Browser
   ↓
  ZAP
   ↓
Web Server
```

and on the way back:

```text
Web Server
   ↓
  ZAP
   ↓
Browser
```

Because ZAP sits in the middle, it can:

```text
observe
record
analyse
intercept
modify
resend
scan
```

web traffic.

The security lesson that made the most sense to me was:

> **What the browser permits is not necessarily what the server will receive.**

A browser may restrict what I can type or change through the interface, but the underlying HTTP request can potentially be modified after those browser-side checks.

That is why security-sensitive validation also has to happen on the server.
