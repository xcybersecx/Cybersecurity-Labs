# OWASP ZAP Proxy, HUD and Request Interception Practical

**Completed:** 23 August 2026  
**Environment:** Kali Linux and Firefox  
**Tool:** OWASP ZAP 2.17.0  
**Training Target:** `testaspnet.vulnweb.com`

## Overview

This practical focused on understanding how OWASP ZAP works as an intercepting web proxy.

The objective was to observe communication between a browser and a web application, understand the difference between passive and active scanning, inspect HTTP requests and responses, and begin learning how requests can be intercepted and modified before reaching the server.

The main traffic flow was:

**Browser → ZAP → Web Server**

and:

**Web Server → ZAP → Browser**

ZAP's position between the browser and server allows it to:

**observe → record → analyse → intercept → modify → resend → scan**

---

# 1. Configuring the ZAP Root CA Certificate

Firefox was configured to trust the ZAP Root CA certificate.

This is important when inspecting HTTPS traffic because HTTPS communication is encrypted.

For ZAP to inspect HTTPS requests and responses, it acts as an intermediary between the browser and the target server.

Firefox therefore needs to trust certificates generated by ZAP during interception.

This allows the browser to communicate through ZAP without immediately rejecting the intercepted HTTPS connection.

## What I Learned

HTTPS interception requires the browser to trust the proxy's certificate authority.

Without that trust relationship, the browser would warn that the generated certificate could not be trusted.

# 5. Passive and Active Scanning

One of the important concepts introduced during the session was the difference between passive and active scanning.

## Passive Scanning

Passive scanning analyses requests and responses that are already passing through ZAP.

ZAP observes the traffic without deliberately modifying it or sending attack payloads.

In simple terms:

**Passive = observe and analyse**

## Active Scanning

Active scanning sends specially constructed requests and payloads to the target in order to test for vulnerabilities.

In simple terms:

**Active = actively test**

Active scanning should only be performed against systems that are authorised for security testing.

# 8. Enabling Disabled or Read-Only Fields

The HUD demonstrated that HTML form fields can be:

- editable;
- disabled; or
- read-only.

ZAP's Show/Enable functionality can expose or enable fields that the browser interface normally prevents a user from editing.

This introduced an important security principle:

**Client-side restrictions should not be treated as security boundaries.**

A browser may prevent a user from entering or modifying a value through the interface, but the underlying HTTP request can still potentially be changed.

The server must therefore validate security-sensitive input itself.

---

# 9. Request Interception

The HUD tutorial included an HTML5 number field restricted to values between:

```text
1 and 100
```

The objective was to submit a valid number through the browser, intercept the resulting HTTP request in ZAP, and modify the request before it reached the server.

Conceptually:

```text
Browser submits: number=50

        ↓

ZAP intercepts request

        ↓

Tester modifies:
number=50

to:

number=ZAP

        ↓

ZAP forwards request

        ↓

Server receives: number=ZAP
```

## Security Lesson

The browser may enforce a rule such as:

```text
Only numbers between 1 and 100
```

but an intercepting proxy operates after the browser has created the HTTP request.

This means the request may be altered before the server receives it.

Therefore:

**Client-side validation improves usability but cannot replace server-side validation.**

# 12. History, Break and Breakpoints

The troubleshooting process helped clarify three different ZAP concepts.

## History

**History contains traffic that has already passed through ZAP.**

It can be reviewed after the request or response has occurred.

## Break

**Break represents traffic that is currently paused.**

This is the point at which the tester can inspect or modify the message before deciding whether it should continue.

## Breakpoints

**Breakpoints are rules that determine which traffic ZAP should interrupt.**

This distinction helped make ZAP's interception workflow much clearer.

---

# 13. Break Controls

I also identified several controls used when traffic is intercepted.

## Step

Forwards the current message and breaks again on the next relevant request or response.

## Continue

Forwards the current message and continues processing until another breakpoint is encountered.

## Drop

Stops the intercepted request or response from continuing.

Understanding these controls helped explain how an intercepting proxy can influence traffic between the browser and server.

# 14. HTTP Status Codes Encountered

Two important HTTP status codes appeared repeatedly during the session.

## 200 OK

```text
200 OK
```

indicates that the HTTP request was processed successfully and a valid response was returned.

It does not necessarily mean that the user's intended application action succeeded.

## 504 Gateway Timeout

```text
504 Gateway Timeout
```

indicates that a server or intermediary did not receive a response from an upstream system within the required period.

This occurred several times while attempting to reach the training target through ZAP.

The session also highlighted the need to become more familiar with HTTP status-code groups:

```text
2xx = Success
3xx = Redirection
4xx = Client/request-related errors
5xx = Server/upstream errors
```

Important individual codes for further revision include:

```text
200 201
301 302
400 401 403 404
500 502 503 504
```

# What I Learned

This session helped me understand ZAP as more than simply another vulnerability scanner.

The main lessons were:

- ZAP can operate as an intercepting proxy between a browser and a web server.
- HTTPS interception requires the browser to trust ZAP's Root CA.
- The HUD provides ZAP functionality within the browser.
- Passive scanning observes existing traffic.
- Active scanning deliberately tests the application.
- The Sites tree maps discovered application resources.
- GET and POST represent different types of HTTP interaction.
- HTML fields disabled by the browser are not automatically protected from manipulation.
- Client-side validation cannot be relied upon as a security control.
- HTTP requests can be inspected and potentially modified before reaching the server.
- History shows traffic that has already passed.
- Break shows traffic currently being intercepted.
- Breakpoints determine which traffic should be interrupted.
- HTTP status codes describe the HTTP transaction and do not always describe the application-level outcome.
- Tool and network problems are part of practical testing and need to be diagnosed rather than simply ignored.

# Key Takeaway

The most important concept from this practical was the position of ZAP within the communication path:

```text
Browser
   ↓
  ZAP
   ↓
Web Server
```

and:

```text
Web Server
   ↓
  ZAP
   ↓
Browser
```

Because ZAP sits in the middle, it can:

```text
observe
record
analyse
intercept
modify
resend
scan
```

web traffic.

The biggest security lesson was:

> **What the browser permits is not necessarily what the server will receive.**

A browser may prevent a user from submitting a particular value, but the underlying HTTP request can potentially be modified after the browser has applied its restrictions.

Security-sensitive validation must therefore also be enforced by the server.
